# GPU Sharing: Fractions & Memory

KAI Scheduler supports GPU sharing, allowing multiple pods to utilize the same GPU device efficiently by allocating a GPU device to multiple pods.

The scheduler decides which node and device can satisfy the fractional request. During binding, KAI's binder creates a reservation Pod with GPU access in the `kai-resource-reservation` namespace. These reservation Pods need a GPU-capable runtime with NVML support; that is the mechanism KAI uses to reserve and identify the actual device before binding the fractional workload Pods to that same GPU.

A reservation Pod is tied to the shared physical GPU reservation, not to each individual workload Pod. In this example, three Pods request `0.2`, `0.3`, and `0.5` GPU from the same KAI queue. The queue has `quota: 1` and `limit: 1`, so the total request can fit only because the Pods are accounted fractionally. If all three shares land on the same physical GPU, KAI creates one reservation Pod for that GPU reservation and accounts the three workload Pods against it. The reservation Pod is not a user workload; it is a scheduler bookkeeping object that prevents the same shared device from being over-allocated beyond the requested fractions.


<Callout type="warning" title="Memory isolation">
By default, KAI Scheduler does not enforce memory allocation limits or perform memory isolation between processes. Please use [HAMI](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/docs/gpu-sharing/hami/README.md) to enforce memory isolation.
</Callout>

<Callout type="warning" title="Simulation caveat">
This CPU-only lab can show the scheduling intent and reservation pattern. It cannot enforce real GPU memory isolation. Production enforcement needs hardware and runtime support such as MPS or HAMi.
</Callout>

In this chapter, the 20%, 30%, and 50% workloads run in `namespace-a`, `namespace-b`, and `namespace-c`. They all use the `gpu-sharing-demo` queue, whose GPU quota and limit are both `1`. KAI can still run all three Pods because `0.2 + 0.3 + 0.5 = 1.0`.

The key request is the `gpu-fraction` annotation on the Pod. Do not add a full GPU request or a DRA claim to this example: that would make KAI account the full GPU plus the fraction. The annotation is the scheduling request for this fractional GPU-sharing path.

```yaml
metadata:
  labels:
    kai.scheduler/queue: gpu-sharing-demo
  annotations:
    gpu-fraction: "0.2"
spec:
  schedulerName: kai-scheduler
```

Display the setup manifest. It creates the three namespaces and the `gpu-sharing-demo` queue with `quota: 1` and `limit: 1`.

```bash
cat manifests/19-gpu-sharing/00-setup.yaml
```

Apply the setup.

```bash
kubectl apply -f manifests/19-gpu-sharing/00-setup.yaml
```

Confirm that the queue exists and is limited to one GPU.

```bash
kubectl get queue gpu-sharing-demo -o yaml
```

Display the 20% workload manifest.

```bash
cat manifests/19-gpu-sharing/01-fraction-20.yaml
```

Create the 20% workload in `namespace-a`.

```bash
kubectl apply -f manifests/19-gpu-sharing/01-fraction-20.yaml
```

Display the 30% workload manifest.

```bash
cat manifests/19-gpu-sharing/02-fraction-30.yaml
```

Create the 30% workload in `namespace-b`.

```bash
kubectl apply -f manifests/19-gpu-sharing/02-fraction-30.yaml
```

Display the 50% workload manifest.

```bash
cat manifests/19-gpu-sharing/03-fraction-50.yaml
```

Create the 50% workload in `namespace-c`.

```bash
kubectl apply -f manifests/19-gpu-sharing/03-fraction-50.yaml
```

Inspect the 20% Pod and note the node selected by KAI.

```bash
kubectl get pods -n namespace-a -o wide
```

Inspect the 30% Pod and compare its node placement.

```bash
kubectl get pods -n namespace-b -o wide
```

Inspect the 50% Pod. The important observation is that three Pods can be `Running` even though the queue is capped at one GPU.

```bash
kubectl get pods -n namespace-c -o wide
```

Show all three chapter workloads in one view. They should all be `Running` once KAI has placed the fractional requests.

```bash
kubectl get pods -A -l kai-scheduler-101/chapter=19 -o wide
```

Describe one sharing Pod and inspect the `gpu-fraction` annotation.

```bash
kubectl describe pod -n namespace-a gpu-share-20
```

Look for reservation Pods. In the ideal shared-placement case for this example, you should see one reservation Pod representing the shared physical GPU reservation. The reservation Pod normally lives in the `kai-resource-reservation` namespace, while the workload Pods can live in different namespaces.

```bash
kubectl get pods -n kai-resource-reservation
```

Inspect KAI scheduler logs to understand the placement decisions. Useful keywords to look for in the output are `gpu-fraction`, `reservation`, `ResourceReservation`, `gpu-sharing-demo`, and the Pod names `gpu-share-20`, `gpu-share-30`, and `gpu-share-50`.

```bash
kubectl logs -n kai-scheduler deploy/kai-scheduler-default --tail=200
```

## Clean Up

Delete the first workload namespace so fractional sharing Pods do not remain scheduled.

```bash
kubectl delete namespace namespace-a --ignore-not-found
```

Delete the second workload namespace.

```bash
kubectl delete namespace namespace-b --ignore-not-found
```

Delete the third workload namespace.

```bash
kubectl delete namespace namespace-c --ignore-not-found
```

Delete the queue created for this chapter.

```bash
kubectl delete queue gpu-sharing-demo --ignore-not-found
```

## What Just Happened

You expressed fractional GPU intent with Pod annotations. KAI accounted three Pods as fractions of one GPU, created or used a reservation object for the shared device, and allowed the Pods to run under a queue capped at one GPU. That scheduling accounting should not be confused with runtime memory isolation.

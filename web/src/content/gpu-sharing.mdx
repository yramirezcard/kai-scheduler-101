# Device Plugin & GPU Sharing

Until this point, the lab has used Kubernetes Dynamic Resource Allocation (DRA). That is the modern practice for allocating GPUs through device claims, and it is the right mental model for the earlier chapters where Pods request whole GPUs through `ResourceClaimTemplate` objects.

KAI's GPU sharing path is different today. Fractional GPU scheduling uses the device-plugin style GPU resource path plus KAI reservation Pods. In other words, for this chapter you will switch the fake GPU environment from DRA-backed `ResourceSlice` capacity to classic `nvidia.com/gpu` capacity, verify a normal one-GPU Pod, and then submit fractional Pods with KAI's `gpu-fraction` annotation.

## Device Plugin

First, remove any chapter workloads that still own DRA claims. The mode switch is easier to understand when old `ResourceClaim` objects are not mixed into the output.

```bash
kubectl delete namespaces namespace-a namespace-b namespace-c --ignore-not-found
kubectl delete pods -A -l kai-scheduler-101/chapter=19 --ignore-not-found
```

Switch the fake GPU operator from DRA mode to device-plugin mode. The fake GPU shape stays the same: each simulated node still advertises eight H100-style GPUs with 80 GiB of memory. Only the Kubernetes allocation path changes.

```bash
helm upgrade -i gpu-operator oci://ghcr.io/run-ai/fake-gpu-operator/fake-gpu-operator \
  -n gpu-operator --create-namespace \
  --version 0.2.0 \
  --set 'topology.nodePools.default.gpuCount=8' \
  --set 'topology.nodePools.default.gpuProduct=NVIDIA-H100-80GB-HBM3' \
  --set 'topology.nodePools.default.gpuMemory=81920' \
  --set 'draPlugin.enabled=false' \
  --set 'kwokDraPlugin.enabled=false' \
  --set 'devicePlugin.enabled=true' \
  --set 'kwokGpuDevicePlugin.enabled=true'
```

Now verify a normal one-GPU allocation through the device-plugin path. This test intentionally uses `resources.limits.nvidia.com/gpu: 1` and does not create a DRA claim.

```bash
kubectl create namespace device-plugin-demo --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -f - <<'EOF'
apiVersion: scheduling.run.ai/v2
kind: Queue
metadata:
  name: device-plugin-demo
spec:
  resources:
    gpu: { quota: 1, limit: 1, overQuotaWeight: 1 }
---
apiVersion: v1
kind: Pod
metadata:
  name: one-gpu-device-plugin
  namespace: device-plugin-demo
  labels:
    kai.scheduler/queue: device-plugin-demo
spec:
  schedulerName: kai-scheduler
  restartPolicy: Never
  tolerations: [ { key: kwok.x-k8s.io/node, operator: Exists, effect: NoSchedule } ]
  containers:
    - name: workload
      image: ubuntu:22.04
      command: ["bash", "-lc"]
      args: ["echo scheduled with one device-plugin GPU; sleep 3600"]
      resources:
        limits:
          nvidia.com/gpu: 1
EOF
```

Inspect the Pod placement. The Pod should become `Running` on one of the simulated GPU nodes.

```bash
kubectl get pod -n device-plugin-demo one-gpu-device-plugin -o wide
```

Clean up the one-GPU smoke test before starting the fractional example.

```bash
kubectl delete namespace device-plugin-demo --ignore-not-found
kubectl delete queue device-plugin-demo --ignore-not-found
```

## GPU Sharing

KAI Scheduler supports GPU sharing, allowing multiple pods to utilize the same GPU device efficiently by allocating a GPU device to multiple pods.

The scheduler decides which node and device can satisfy the fractional request. During binding, KAI's binder creates a reservation Pod with GPU access in the `kai-resource-reservation` namespace. These reservation Pods need a GPU-capable runtime with NVML support; that is the mechanism KAI uses to reserve and identify the actual device before binding the fractional workload Pods to that same GPU.

A reservation Pod is tied to the shared physical GPU reservation, not to each individual workload Pod. In this example, three Pods request `0.2`, `0.3`, and `0.5` GPU from the same KAI queue. The queue has `quota: 1` and `limit: 1`, so the total request can fit only because the Pods are accounted fractionally. If all three shares land on the same physical GPU, KAI creates one reservation Pod for that GPU reservation and accounts the three workload Pods against it. The reservation Pod is not a user workload; it is a scheduler bookkeeping object that prevents the same shared device from being over-allocated beyond the requested fractions.


<Callout type="warning" title="Memory isolation">
By default, KAI Scheduler does not enforce memory allocation limits or perform memory isolation between processes. Please use [HAMI](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/docs/gpu-sharing/hami/README.md) to enforce memory isolation.
</Callout>

<Callout type="warning" title="Simulation caveat">

In this chapter, the 20%, 30%, and 50% workloads run in `namespace-a`, `namespace-b`, and `namespace-c`. They all use the `gpu-sharing-demo` queue, whose GPU quota and limit are both `1`. KAI can still run all three Pods because `0.2 + 0.3 + 0.5 = 1.0`.

The key request is the `gpu-fraction` annotation on the Pod. Do not add a full GPU request or a DRA claim to this example: that would make KAI account the full GPU plus the fraction. The annotation is the scheduling request for this fractional GPU-sharing path.

```yaml
metadata:
  labels:
    kai.scheduler/queue: gpu-sharing-demo
  annotations:
    gpu-fraction: "0.2"
spec:
  schedulerName: kai-scheduler
```

## What Just Happened

You temporarily moved the simulated GPU fleet from DRA allocation to the device-plugin allocation path, verified a normal one-GPU Pod with `nvidia.com/gpu`, and then expressed fractional GPU intent with Pod annotations. KAI accounted three Pods as fractions of one GPU, created or used a reservation object for the shared device, and allowed the Pods to run under a queue capped at one GPU. After the demo, you restored the fake GPU operator to DRA mode. That scheduling accounting should not be confused with runtime memory isolation.

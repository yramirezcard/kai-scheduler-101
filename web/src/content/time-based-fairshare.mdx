# Time-Based Fairshare

Point-in-time fair-share only looks at the current scheduling cycle. That is useful, but it has no memory: if two queues are tied and both have an endless backlog of large jobs, the same queue can keep winning because of tie-breakers such as queue order or creation time.

Time-based fairshare adds memory to over-quota scheduling. **KAI tracks historical resource usage per queue and resource type**. A queue that has consumed many GPU-hours recently is penalized when over-quota resources are divided again, while a queue with little recent over-quota usage is boosted. Over a long enough window, queues with the same over-quota weight should receive similar GPU-time.

This does **not** replace the normal guarantees:

- Deserved quota still comes first.
- Queue priority still comes before over-quota weight.
- Time-based fairshare only adjusts the over-quota division within the relevant priority tier.

The animation below uses only two queues. Vision runs first and accumulates GPU-time. LLM has low historical usage, so its effective fair share rises and it gets the next over-quota turn. After LLM runs long enough, its history increases and Vision becomes comparatively starved. The result is the oscillation shown in the source diagrams: resources move back and forth instead of one team monopolizing the over-quota pool.

KAI uses historical usage only when the scheduler can read usage data, so the setup has two parts: enable Prometheus collection in the KAI `Config`, then configure the `SchedulingShard` with `usageDBConfig`. The optional `kValue` controls how strongly historical usage affects over-quota fair-share calculations, and `halfLifePeriod` controls time decay. If `halfLifePeriod` is omitted, time decay is off by default.

  Scheduling shards partition a cluster into independent scheduling domains. The concept will be further demonstrated in Part VII.
  This lab only shows how to configure the feature, it does not demonstrated it as no real GPU usage is traced in this environment due to the simulated GPUs.

First, display the example `SchedulingShard` configuration. The important fields are `spec.usageDBConfig.clientType: prometheus`, `spec.usageDBConfig.usageParams`, and `spec.kValue`.

```bash
cat manifests/09-time-fairshare/scheduling-shard-time-fairshare.yaml
```

Enable Prometheus support in the KAI config. This requires Prometheus support to be available in the cluster, as described in the metrics and observability chapter.

```bash
kubectl patch config kai-config --type merge -p '{"spec":{"prometheus":{"enabled":true}}}'
```

Inspect the KAI config so you can confirm the Prometheus setting and any status conditions.

```bash
kubectl describe config kai-config
```

Apply the example shard configuration.

```bash
kubectl apply -f manifests/09-time-fairshare/scheduling-shard-time-fairshare.yaml
```

Read the shard back from the API.

```bash
kubectl get schedulingshard time-fairshare-demo -o yaml
```

List all shards so you can see the default shard and lab-created examples together.

```bash
kubectl get schedulingshard
```

## Clean Up

Delete the example shard so later placement and shard chapters start from their own configuration.

```bash
kubectl delete schedulingshard time-fairshare-demo --ignore-not-found
```

## What Just Happened

You saw where historical fairness is configured and how to reason about it.  Without `usageDBConfig`, the scheduler uses normal point-in-time fair-share behavior. With Prometheus-backed usage data configured, historical usage becomes part of over-quota allocation and reclaim decisions. The lab keeps the hands-on portion light because meaningful time-based behavior requires elapsed time, persistent usage history, Prometheus-backed accounting, and enough workload churn to make the oscillation visible.

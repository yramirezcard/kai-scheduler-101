# PodGroups & Gang Scheduling

Distributed AI workloads often need several Pods to start together. If one worker starts without the others, it may waste capacity while waiting for its peers, block distributed initialization, or fail training. Gang scheduling gives KAI a larger scheduling unit than a single Pod.

<GangSchedulingAnimation />

This hands-on starts by submitting workloads to fill the queue quota. Then you submit an eight-Pod gang and confirm that it stays pending while there are no free GPUs to satisfy the `batch-min-member` requirement. Finally, you make space in the cluster by deleting one of the running jobs and confirm that the pending gang can be scheduled once eight GPUs become available together.

```bash
cat manifests/12-gang/01-setup.yaml
```

Create the namespace, ResourceClaimTemplate, and a Queue with 12 GPUs as quota and limit 16 GPUs.

```bash
kubectl apply -f manifests/12-gang/01-setup.yaml
```

Apply the PriorityClass manifest used by the filler and gang Pods.

```bash
kubectl apply -f manifests/10-priority/priority-classes.yaml
```

Display the filler workloads. It creates 2 Jobs, which should occupy the quota set in the queue.

```bash
cat manifests/12-gang/02-fill-gpus.yaml
```

Create the filler workloads first.

```bash
kubectl apply -f manifests/12-gang/02-fill-gpus.yaml
```

Confirm the filler Pods are scheduled across the simulated nodes.

```bash
kubectl get pods -n kai-lab12 -l app=fill-all-gpus -o wide
```

Display the gang Job manifest. The annotation `kai.scheduler/batch-min-member: "8"` tells KAI that eight Pods must be schedulable together before the workload should start.

```bash
cat manifests/12-gang/03-gang-job.yaml
```

Create the gang workload. Notice that even though the Queue has already filled the quota capacity, there is a Queue limit of 4 extra GPUs; however, the gang workload requires 8 Pods, so the batch minimum cannot be satisfied.

```bash
kubectl apply -f manifests/12-gang/03-gang-job.yaml
```

List the gang Pods. They should remain pending because KAI cannot satisfy the batch minimum while all 12 GPUs are occupied.

```bash
kubectl get pods -n kai-lab12 -l app=gang-four -o wide
```

List PodGroups created for the namespace. KAI's podgrouper turns workload ownership into scheduling groups, and the gang PodGroup is where the minimum member requirement becomes visible.

```bash
kubectl get podgroups -n kai-lab12
```

Describe the PodGroups to inspect scheduling status and conditions.

```bash
kubectl describe podgroups -n kai-lab12
```

Read recent events in the namespace. Pending is expected here: the gang minimum prevents KAI from starting only one, two, or three workers.

```bash
kubectl get events -n kai-lab12 --sort-by=.lastTimestamp
```

Inspect scheduler logs while the gang is pending.

```bash
kubectl logs -n kai-scheduler deploy/kai-scheduler-default --tail=200
```

Delete the fill-four-gpus workload to free the 4 GPUs missing.

```bash
kubectl delete -f manifests/12-gang/02-fill-gpus.yaml
```

Watch the gang Pods again. Once capacity is free, the pending eight-Pod gang should schedule together because its batch minimum can now be satisfied.

```bash
kubectl get pods -n kai-lab12 -l app=gang-eight -o wide
```

Inspect scheduler logs again to correlate the successful scheduling decision with the changed cluster state.

```bash
kubectl logs -n kai-scheduler deploy/kai-scheduler-default --tail=200
```

## Clean Up

Delete the gang workload.

```bash
kubectl delete -f manifests/12-gang/03-gang-job.yaml --ignore-not-found
```

Delete the setup manifest. This removes the namespace, ResourceClaimTemplate, and queue used by the scenario.

```bash
kubectl delete -f manifests/12-gang/01-setup.yaml --ignore-not-found
```

If the namespace is still terminating, explicitly ask Kubernetes to remove it.

```bash
kubectl delete namespace kai-lab12 --ignore-not-found
```

## What Just Happened

You moved from Pod scheduling to group scheduling. KAI held the four-Pod gang while the cluster had no free GPUs, then scheduled it after enough capacity became available. The important behavior is that KAI did not start a partial distributed job: `batch-min-member: "4"` made four feasible workers the minimum acceptable scheduling decision.

# Bin-Packing vs Spread & Consolidation

Placement strategy changes how KAI chooses among feasible nodes. Spread distributes work, which can improve fault tolerance and reduce hotspots. Bin-pack fills fewer nodes first, which can reduce fragmentation and leave larger empty regions for future gangs.

Consolidation uses the same intuition after work is already running. If workloads are scattered in a way that leaves the cluster fragmented, the scheduler can repack movable workloads to improve utilization, but only when the move can be completed safely. That is why Consolidate appears early in the scheduling cycle: it tries to improve placement before disruptive actions such as reclaim or preemption are needed.

KAI configures placement at the `SchedulingShard` level. The official shard configuration supports a `placementStrategy` map per resource, for example `cpu: spread`, `gpu: spread`, `cpu: binpack`, or `gpu: binpack`. This lab uses one-GPU DRA claims so the placement effect is tied to GPU fragmentation, which is the resource you usually care about in KAI.

## Clean Up

Delete the placement example shards so they do not remain in the scheduler configuration.

```bash
kubectl delete schedulingshard spread-demo binpack-demo --ignore-not-found
```

Delete the spread namespace.

```bash
kubectl delete namespace kai-lab16-spread --ignore-not-found
```

Delete the bin-pack namespace.

```bash
kubectl delete namespace kai-lab16-binpack --ignore-not-found
```

Delete the queues created for the two placement strategies.

```bash
kubectl delete queue spread-demo binpack-demo --ignore-not-found
```

Remove only the temporary placement labels from the existing KWOK nodes.

```bash
kubectl label node kwok-gpu-01 kwok-gpu-02 kwok-gpu-03 kwok-gpu-04 kai.scheduler/node-pool-
```

## What Just Happened

You reused the four simulated GPU nodes and temporarily partitioned them into two shard-local placement policies. Spread optimized for distribution. Bin-pack optimized for consolidation by filling fewer nodes first. The right choice depends on the workload: interactive services often prefer spread for resilience, while gang-heavy training clusters often benefit from bin-pack because it preserves larger contiguous free regions.

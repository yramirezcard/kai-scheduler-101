# Topology-Aware Scheduling

Topology-aware scheduling places related Pods with awareness of physical or logical domains. On real hardware those domains might be blocks, racks, hosts, NVLink domains, or failure zones. In this lab they are labels on KWOK nodes.

KAI gets topology information from two places:

- Kubernetes node labels describe where each node belongs, such as `kai.scheduler/topology-block`, `kai.scheduler/topology-rack`, and `kubernetes.io/hostname`.
- The KAI `Topology` CRD defines the ordered hierarchy of those labels. In this lab, `lab-topology` is `block -> rack -> host`.

A minimal `Topology` object maps each hierarchy level to a Kubernetes node label:

```yaml
apiVersion: kai.scheduler/v1
kind: Topology
metadata:
  name: lab-topology
spec:
  levels:
    - nodeLabel: kai.scheduler/topology-block
    - nodeLabel: kai.scheduler/topology-rack
    - nodeLabel: kubernetes.io/hostname
```

Workloads opt into topology-aware placement with annotations. `kai.scheduler/topology` selects the Topology object. A required placement annotation sets the broadest domain that must contain the whole workload. A preferred placement annotation asks the scheduler to keep Pods closer together inside that required boundary when possible.

The first sample workload requires block-level placement and prefers rack-level locality. With the 24-node KWOK fleet, there are two blocks, each with three racks, and each rack has four hosts. A four-worker job would be too small to show why that bigger shape matters, so this chapter uses a 12-worker GPU gang. The expected result is that KAI keeps all workers inside one block and, when feasible, prefers one rack inside that block. If the preferred rack cannot fit all workers, the scheduler can still place within the required block boundary rather than spreading across both blocks.

KAI also supports Multi-Level Topology Aware Scheduling for hierarchical PodGroups. Instead of giving one topology rule to the whole workload, each SubGroup can carry its own `topologyConstraint`. This is a natural fit for Grove, which you introduced earlier: the root `PodCliqueSet` can require one block, prefill and decode `PodCliqueScalingGroup`s can each require a rack, and tightly coupled cliques can request host-level packing. The second hands-on manifest uses Grove CRDs to describe 20 one-GPU Pods so the multi-level constraints are visible on the 24-node topology.

## What Just Happened

You turned labels into a topology tree and asked KAI to place two topology-aware workloads. The 12-GPU gang made the 24-node cluster meaningful by requiring a larger placement decision than a tiny four-worker job. The multi-level serving example then showed the hierarchical case: the root workload stays within one block, mid-level prefill and decode groups can each express rack locality, and leaf groups can add stricter host or rack requirements.

# Hierarchical PodGroups & SubGroups

Some distributed systems have nested roles. A disaggregated serving stack might need a router, a prefill group, and a decode group before it can serve traffic. Within prefill and decode, there can also be leaders and workers that must be co-located for fast communication. A single flat `minMember` value is too blunt for that shape.

KAI's hierarchical PodGroup design keeps the root all-or-nothing scheduling contract while adding smaller SubGroups inside it. That gives the scheduler more structure:

- The root `PodGroup` represents the whole workload and points to a KAI queue.
- `minSubGroup` on the root says how many direct child SubGroups must be satisfied before the workload is schedulable.
- A mid-level SubGroup can also use `minSubGroup` to require its own children.
- A leaf SubGroup uses `minMember` to say how many Pods in that role must fit together.
- A Pod is assigned to a leaf SubGroup with the `kai.scheduler/subgroup-name` label.
- Topology constraints can be applied at the root, mid-level, or leaf level so tightly coupled roles can be placed together without forcing the whole serving stack onto one node.

A minimal hierarchical `PodGroup` shape looks like this. The root needs all three direct children, while `prefill` and `decode` are mid-level groups that each require one child group to be satisfied.

```yaml
apiVersion: scheduling.run.ai/v2
kind: PodGroup
metadata:
  name: disaggregated-serving
  namespace: kai-lab14
spec:
  queue: grove-demo
  minSubGroup: 3
  subGroups:
    - name: router
      minMember: 1
    - name: prefill
      minSubGroup: 1
    - name: prefill-workers
      parent: prefill
      minMember: 2
    - name: decode
      minSubGroup: 1
    - name: decode-workers
      parent: decode
      minMember: 2
```

The matching Pods would carry `kai.scheduler/subgroup-name: router`, `prefill-workers`, or `decode-workers` so KAI can attach each Pod to the right leaf in the hierarchy.

## Introducing Grove

Grove is a Kubernetes API for describing AI inference systems as one declarative workload instead of a loose collection of Deployments, Services, startup scripts, and scheduler-specific annotations. Its motivation is very practical: modern inference stacks are rarely just one Pod. A disaggregated serving system can have a router, prefill components, decode components, leaders, workers, and tightly coupled multi-node model replicas. Those pieces often need to scale together, start in a controlled order, and land with enough topology awareness that the serving path is usable.

Grove gives that application shape a Kubernetes-native API. A `PodCliqueSet` is the top-level serving system. A `PodClique` represents one role, such as a router or decode worker. A `PodCliqueScalingGroup` ties multiple cliques together so they scale as one unit. A scheduler-facing `PodGang` represents the group scheduling contract that says "these Pods only make sense if the required roles can start together."

That is where KAI fits. Grove owns the inference topology and reconciles the application-facing CRDs into Pods and gang scheduling objects. KAI remains the scheduler backend that evaluates queues, priority, fairness, topology, and placement when those Pods are submitted with `schedulerName: kai-scheduler`. In other words, Grove describes what the serving system is; KAI decides when and where it can run.

Confirm the Grove operator is installed. The bootstrap installs Grove into `grove-system` by default.

```bash
kubectl get pods -n grove-system
```

Inspect the Grove CRDs registered by the Helm chart. These are the APIs the operator watches and reconciles.

```bash
kubectl get crd podcliquesets.grove.io podcliquescalinggroups.grove.io podcliques.grove.io podgangs.scheduler.grove.io
```

Display the disaggregated serving manifest. This manifest creates a KAI queue and a Grove `PodCliqueSet` with five roles: router, prefill leader, prefill workers, decode leader, and decode workers. It sets two top-level `PodCliqueSet` replicas for availability, then groups prefill and decode with `PodCliqueScalingGroup` entries so each multi-role component scales and schedules together.

```bash
cat manifests/14-hierarchical-podgroups/02-grove-disaggregated-serving.yaml
```

Apply the serving example.

```bash
kubectl apply -f manifests/14-hierarchical-podgroups/02-grove-disaggregated-serving.yaml
```

Inspect the top-level Grove object. Its status is the first place to check whether Grove accepted and started reconciling the serving topology.

```bash
kubectl get podcliquesets.grove.io -n kai-lab14 -o wide
```

Describe the `PodCliqueSet` for detailed reconciliation status and events.

```bash
kubectl describe podcliqueset -n kai-lab14 multinode-disaggregated
```

List the role-specific `PodClique` resources that Grove created from the template.

```bash
kubectl get podcliques.grove.io -n kai-lab14 -o wide
```

List the `PodCliqueScalingGroup` resources. The prefill group contains the prefill leader and workers; the decode group contains the decode leader and workers.

```bash
kubectl get podcliquescalinggroups.grove.io -n kai-lab14 -o wide
```

Inspect the scheduler-facing `PodGang` objects created by Grove.

```bash
kubectl get podgangs.scheduler.grove.io -n kai-lab14 -o yaml
```

List the generated Pods and their node placement. These Pods use `schedulerName: kai-scheduler`, so KAI is responsible for placement.

```bash
kubectl get pods -n kai-lab14 -o wide
```

Read namespace events. Events usually show the first useful signal if the Grove object, PodGang, or generated Pods are waiting on a scheduling condition.

```bash
kubectl get events -n kai-lab14 --sort-by=.lastTimestamp
```

Inspect the Grove operator logs. These logs explain what Grove reconciled from the `PodCliqueSet`: cliques, scaling groups, gangs, and Pods.

```bash
kubectl logs -n grove-system -l app.kubernetes.io/name=grove-operator --tail=200
```

Inspect the KAI scheduler logs. These logs are the scheduler-side view: queue admission, gang feasibility, and placement decisions for the generated Pods.

```bash
kubectl logs -n kai-scheduler deploy/kai-scheduler-default --tail=200
```

## Clean Up

Delete the Grove serving example.

```bash
kubectl delete -f manifests/14-hierarchical-podgroups/02-grove-disaggregated-serving.yaml --ignore-not-found
```

If the namespace remains because generated Pods are still terminating, remove it explicitly.

```bash
kubectl delete namespace kai-lab14 --ignore-not-found
```

Delete the cluster-scoped queue if it remains.

```bash
kubectl delete queue grove-demo --ignore-not-found
```

## What Just Happened

You used Grove as the application-facing API and KAI as the scheduling backend. The `PodCliqueSet` expressed the disaggregated serving topology. Grove expanded that into role-specific cliques, grouped prefill/decode components, scheduler-facing PodGangs, and Pods. KAI then handled the actual scheduling decisions for those Pods through the `kai-scheduler` scheduler name and the `grove-demo` queue label.
